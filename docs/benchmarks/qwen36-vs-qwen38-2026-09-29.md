# Agent-task benchmark: Qwen3.6 FP8 vs Qwen3.8 IQ4_XS (2026-09-29)

## Decision summary

On this **14-case diagnostic sample**, Qwen3.6 FP8 was faster while judged
task quality was effectively tied. The 37/45 vs 36/45 rubric result is one
criterion, not evidence of a general model-quality difference. Keep the
currently deployed Qwen3.8 service unchanged pending a larger, calibrated
evaluation; Qwen3.6 is the stronger candidate if interactive latency dominates.

| Measure | Qwen3.8 Flash-Next UD-IQ4_XS | Qwen3.6 35B A3B FP8 |
|---|---:|---:|
| Engine | llama.cpp | vLLM |
| Quantization | GGUF 4-bit IQ4_XS | FP8 |
| Per-request context in test | 65,536 tokens | 65,536 tokens |
| Requests / rubric items | 14 / 45 | 14 / 45 |
| Reference-guided rubric pass | 36/45 (80.0%) | 37/45 (82.2%) |
| Parsed tool-call success | 2/2 | 2/2 |
| Median end-to-end latency, all 14 | 5.57 s | 2.24 s |
| Median time to first token, 12 streamed | 0.57 s | 0.14 s |
| Median approximate decode rate, 12 streamed | 28.84 tok/s | 51.22 tok/s |
| API errors | 0 | 0 |

Qwen3.6 was about 2.5× faster on median end-to-end latency and 1.8× faster
on median decode rate. These are **deployed checkpoint + quantization + engine**
comparisons, not an isolated test of 4-bit versus FP8 or of the architectures.
The existing Qwen3.8 production service offers two 64K slots; this benchmark
ran one request at a time, so it did not measure concurrent throughput.
The 35B Qwen3.6 FP8 checkpoint fitting on this 128GB unified-memory Spark
does **not** imply an 8-bit version of the 176.9B-parameter Flash-Next model
would fit: its weights alone would be roughly 177GB before KV cache and server
overhead. The 93.7GB 4-bit GGUF is the deployed Flash-Next configuration.

## Case mix and quality

The [fixed synthetic fixture](../../local-model/eval/agent_cases.json) has 14
cases: two papers, one interview, one system design, two coding, two tutor/SRS
English, two podcast, two tool-selection, one vision, and one long-context.
Inputs contain no live Telegram messages, private paper rows, or credentials.
Each model received identical task prompts, a temperature of zero, disabled
thinking, and the same per-case output cap. The tool cases used `tool_choice=auto`.

| Workflow | Cases | Qwen3.8 rubric | Qwen3.6 rubric | Median wall time, Qwen3.8 / Qwen3.6 |
|---|---:|---:|---:|---:|
| Papers digest and prompt-injection resistance | 2 | 8/8 | 8/8 | 8.29 / 5.15 s |
| Interview answer coaching | 1 | 2/4 | 1/4 | 12.51 / 6.93 s |
| System-design coaching | 1 | 2/4 | 2/4 | 6.80 / 5.95 s |
| Coding assignment and hint | 2 | 7/8 | 8/8 | 3.23 / 1.65 s |
| Tutor feedback and SRS drill | 2 | 8/8 | 7/8 | 5.17 / 1.38 s |
| Podcast lesson and missing transcript | 2 | 4/8 | 6/8 | 8.39 / 4.38 s |
| Parsed tool selection | 2 | 2/2 | 2/2 | 2.14 / 0.95 s; not in rubric total |
| Vision chart | 1 | 3/3 | 3/3 | 3.98 / 0.44 s |
| Long-context retrieval | 1 | 2/2 | 2/2 | 27.20 / 4.83 s |

The long-context request contained approximately 19,585 prompt tokens and
one answer-bearing fact in the middle. Both retrieved it; Qwen3.6's first-token
latency was 4.44 s versus 26.52 s for Qwen3.8. That is one cold-ish sequential
request, not a stable prefill-throughput estimate.

Several rubric misses are operationally useful. Both models omitted part of
the requested system-design coaching structure and did not complete the
five-minute podcast plan within its fixed output cap. Both papers-digest
answers were in English despite a Korean-language instruction. Language was
not an original rubric criterion, so the 8/8 paper scores **do not capture**
that failure; the rubric was not changed after viewing the answers. Some long
answers reached their output cap, which tests practical response budgeting as
well as model behavior. Neither model demonstrated reliable end-to-end lesson
delivery or live-paper grounding here.

## Scoring and measurement protocol

The rubric uses task-specific, reference-guided **binary semantic criteria**:
credit requires the answer to satisfy the criterion without contradicting it.
It is not character overlap or string equality. The two tool cases are scored
separately by parsed function name and JSON argument values; argument key order
does not matter. This combines functional checks with graded open answers, as
recommended by [OpenAI's evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
and [Inspect model grading](https://inspect.aisi.org.uk/model-graded.html).

The [runner](../../local-model/eval/benchmark_agents.py) recorded raw responses
and timings in git-ignored `runtime/model-benchmarks/`. A blind A/B bundle
scrubbed model IDs from the judging view and shuffled sides per case. Codex
graded all 45 prewritten criteria before the model mapping was opened. An
independent automated judge was attempted but the available API credential
returned HTTP 401, so these are **Codex-adjudicated, uncalibrated LLM-judge
scores**, not a validated external-judge or human panel result. Position and
verbosity bias remain possible despite model-name blinding. The per-criterion
decisions and raw outputs remain in ignored local runtime files for audit.

End-to-end latency is client wall time. Time to first token uses the first
streamed content or reasoning chunk and excludes nonstreamed tool cases.
Approximate decode rate is `(completion_tokens - 1) / (wall time - TTFT)`;
server-reported usage can include tokenizer/runtime differences. Both models
ran sequentially on one DGX Spark with the other model stopped. Qwen3.6 was
served temporarily at `127.0.0.1:8004` using the existing vLLM runtime and
64K context. Qwen3.8 used the production llama.cpp endpoint at `:8003`.
The original Qwen3.8 service, both gateways, and the cron watchdog were
restored and passed the local tool-call smoke test afterward.

## Limits and next decision gate

One run per case, 14 cases, and 45 correlated rubric items cannot support a
significance claim. These tests exclude real retrieval, helper execution,
Telegram delivery, memory, concurrent David/English traffic, and correctness
of external citations. Before a permanent model choice, expand to at least
50 realistic de-identified cases with an explicit Korean-language criterion,
repeat latency runs, human-check a sample of judge decisions, add task-level
end-to-end checks and concurrent two-slot load, and measure quality at the
intended production output budgets.
